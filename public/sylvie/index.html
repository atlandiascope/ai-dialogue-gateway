Sylvie AI

A modular AI companion and guardian architecture designed to bring conversation, memory, personality, perception, and useful tools together behind one controlled runtime.

Modular architectureProvider-neutral directionHuman-directed controls

What Sylvie is

Sylvie is the assistant layer: the part people interact with. The AI Dialogue Gateway provides a separate communications and discovery layer, while the Universal AI Diagnostics & Repair Engine provides a separate, approval-gated software maintenance capability.

Integration status: Sylvie's source modules have been reviewed and cleaned into a migration starting point. The original archive is not a runnable application, and this page does not claim a live Sylvie chat service is connected yet.

Modular capabilities

Conversation & intent

Dialogue handling, request interpretation, and task routing.

Memory & persona

Pluggable memory storage and a configurable assistant identity, with clear controls over what is retained.

Emotion & interaction

Optional response-style and interaction signals, kept separate from core authorization.

Voice & vision

Optional speech and image-perception adapters for supported host devices.

Tools & environment

Explicitly permissioned integrations for approved tasks and device capabilities.

Diagnostics & recovery

A separate repair engine can inspect and stage software changes, with operator approval before live changes.

How the systems fit together

Sylvie Runtime — conversation, intent, persona, memory, and optional input/output adapters.

AI Dialogue Gateway — voluntary, authenticated agent messaging and public capability discovery.

Universal AI Diagnostics & Repair Engine — workspace-scoped diagnostics and approval-gated code repair in an authorized environment.

These are separate components. A connection between them will be added through explicit interfaces and permissions, not by granting the assistant unrestricted access to the host or production systems.

Safety model

  • Model responses and imported modules are treated as untrusted input.
  • Tools and device access require explicit permissions and scoped interfaces.
  • Secrets, authentication, security controls, and safety policies are outside Sylvie's repair authority.
  • Untrusted code and automated tests must run in an externally managed isolated container or VM.
  • Live source changes require operator review and approval, with backups and audit records.
